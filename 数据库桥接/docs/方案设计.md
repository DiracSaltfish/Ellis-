# 银河数据库局域网桥接方案（V1.0）

> 目标：Mac (Apple Silicon) 作为主力开发机，无法运行银河 tgw/AmazingData 的 x86 二进制；
> 在 **Windows x64 机器上部署桥接服务**，把银河「星耀数智」数据以 REST + WebSocket 形式
> 暴露给局域网内 Mac 使用，Mac 侧代码体验尽量贴近原生 AmazingData。

---

## 1. 总体架构

```
┌─────────────────────────── 局域网 ────────────────────────────┐
│                                                                │
│  ┌──────────────────┐   HTTP(REST查询)   ┌──────────────────┐ │      Internet/专线
│  │   Mac 主力开发机  │ ◄───────────────── │                  │ │    ┌──────────────┐
│  │  策略 / 研究 /    │   WebSocket(实时)  │  Windows x64     │ │    │ 银河星耀服务器 │
│  │  Jupyter / 回测   │ ─────────────────► │  桥接服务         │◄├────┤  ip:port     │
│  │                  │                    │  galaxy-bridge   │ │    │  账号 tgw_*  │
│  │ galaxy-bridge    │                    │  FastAPI+Uvicorn │ │    └──────────────┘
│  │ -client (pip)    │                    │  AmazingData+tgw │ │
│  └──────────────────┘                    │  hdf5 本地缓存    │ │
│                                          └──────────────────┘ │
└────────────────────────────────────────────────────────────────┘
```

**职责划分**

| 组件 | 位置 | 职责 |
|---|---|---|
| bridge-server | Windows x64 | 独占银河账号登录、全部 SDK 调用、hdf5 缓存、订阅管线、向 LAN 提供服务 |
| bridge-client | Mac | 纯 Python HTTP/WS 客户端，DataFrame 还原、装饰器风格实时订阅 |
| config.ini | Windows 侧 | ★ 内网服务器侧默认登录信息（银河账号/密码/IP/端口）集中管理 |

## 2. 方案选型对比

| 方案 | 结论 | 说明 |
|---|---|---|
| **A. Windows 原生桥接服务（选定）** | ✅ | 官方支持环境，零兼容风险；Windows 机常开即可 |
| B. WSL2 / Docker 内跑 Linux whl | 备选 | 同一台 Windows 机也可行（linux_py3xx_x64 包），但多一层网络栈，排错复杂，收益小 |
| C. Mac 本机 amd64 容器（Rosetta 转译）+ CentOS7 | 实验性 | libtgw.so 为 RHEL7 老 glibc 构建，Rosetta 能否长期稳定承载未经验证；行情实时性无保障；厂商不支持。见附录 A |
| D. UTM/QEMU 整机 x86 模拟 | ❌ | 慢 10~20 倍，运维成本高 |

## 3. 接口协议

### 3.1 REST（查询面，端口默认 8900）

统一响应信封：
```json
{ "ok": true,  "data": ..., "elapsed_ms": 123 }
{ "ok": false, "err_code": -1, "message": "login fail", "elapsed_ms": 45 }
```

DataFrame 序列化信封（`__type__: df`）：
```json
{ "__type__": "df",
  "columns": ["open","high"], "dtypes": {"open":"float64","trade_time":"datetime64[ns]"},
  "index":   ["2026-08-25T09:31:00"],
  "rows":    [[10.1, 10.2], null→NaN 由客户端还原] }
```
客户端按 `dtypes` 还原 datetime 列；`{code: DataFrame}` 字典逐值打包。

| 方法&路径 | 用途 |
|---|---|
| GET `/health` | 登录状态/版本/订阅概况（无需鉴权，便于探活） |
| GET `/api/v1/meta/methods` | 服务端自省：各分组可用方法列表 |
| POST `/api/v1/call/{group}/{method}` | **通用分发**：group ∈ base/info/market/download，body=`{"args":[...],"kwargs":{...}}`；覆盖全部 ~60 个接口 |
| POST `/api/v1/kline` | 快捷历史K线 `{code_list, begin_date, end_date, period}` |
| POST `/api/v1/snapshot` | 快捷历史快照 `{code_list, begin_date, end_date[, begin_time,end_time]}` |
| GET `/api/v1/code_list/{security_type}` | 快捷代码表 |
| GET `/api/v1/calendar` | 交易日历 |
| POST `/admin/login` `/admin/logout` | 手动重登/登出 |

鉴权：配置 `api_key` 后，除 `/health` 外所有请求需带 `X-API-Key` 头。

### 3.2 WebSocket（实时行情推送，`/ws`）

连接：`ws://<windows-ip>:8900/ws?api_key=...`

```jsonc
// C→S 设置过滤（只收自己关心的）
{"action":"filter","periods":["snapshot","min1"],"codes":["510300.SH","000001.SZ"]}
// codes 含 "*" 表示全收
{"action":"ping"}                                  // C→S 心跳
{"topic":"md","period":"snapshot","data":{...},    // S→C 推送
 "recv_ts":"2026-08-26T09:30:00.123"}
```

- 服务端**单实例订阅管线**对接银河（独占账号、避免重复订阅），收到回调后序列化广播，
  按每个 WS 客户端的 filter 过滤分发。
- 订阅代码集变更通过 `POST /api/v1/sub/reload {"subs":[{"period":"snapshot","code_list":[...]}]}`
  整体重建管线（上游重复订阅幂等）。取消订阅为本地过滤语义。
- 断线自动重连由客户端库负责（指数退避）。

## 4. 服务端内部设计要点（源自 SDK 调研结论）

1. **绕开 ad.login 的 exit() 风险**：直接构造 `tgw.Cfg(username,password,server_vip,server_port,force_logout)`
   → `tgw.Login(cfg, ApiMode.kInternetMode)`，重试/退避/告警全部自管（与 ad.login 内部逻辑等价）。
2. **懒加载三件套**：登录成功后惰性创建 `BaseData/InfoData`；首次用到历史行情时
   取 `get_calendar()` 初始化 `MarketData` 并缓存，每日自动刷新一次日历。
3. **并发控制**：SDK 线程安全性未知 → 全局信号量限流（默认 2），登录态互斥锁保护。
4. **断线自愈**：任一调用抛异常即标记离线并触发后台重连循环（60s 间隔），
   期间请求返回结构化错误而非挂死。
5. **local_path 收口**：客户端永远不传本地路径；kwargs 中 `local_path` 为空时服务端自动替换为
   `[local_cache] root`（如 `D:\AmazingData_local_data\`），享受 hdf5 增量缓存加速。
6. **日志**：文件+控制台双写，tgw 日志 SPI 桥接到 Python logging。

## 5. 默认登录信息（内网服务器侧）

集中在 `bridge-server/config.ini`（随部署包交付，含占位符待一次性填写）：

```ini
[galaxy]
username = tgw_REPLACE_ME        ; 营业部开通权限后提供，tgw_ 开头
password = REPLACE_ME
host     = REPLACE_ME            ; 银河数据服务器 IP
port     = 7000                  ; 端口
api_mode = kInternetMode         ; 或 kColocationMode
force_logout = true              ; 启动时踢旧会话，防多端互踢

[bridge]
listen_host = 0.0.0.0            ; 局域网监听
listen_port = 8900
api_key     = CHANGE_ME_32B      ; 建议 32 位随机串
```

安全要求：
- 密码仅存 Windows 机本地 config.ini；目录设置 NTFS 权限仅本用户可读；**不得提交 git**。
- 支持环境变量覆盖任意项：`GALAXY_BRIDGE_GALAXY_PASSWORD=...` 等（CI/临时调试用）。
- `/health` 只暴露脱敏信息（账号打码 `tgw_****`）。
- 路由器/防火墙将 8900 端口限制为局域网子网访问，**绝不做公网映射**。

## 6. 合规约束（务必遵守）

1. 账号仅供本人使用；桥接仅打通本人名下设备，**不对外提供服务/转发数据**。
2. 同一账号多人同时登录会被停止服务 → 桥接机独占账号 + force_logout。
3. 数据落地（hdf5 缓存）仅存于本人 Windows 机本地。

## 附录 A：Mac 本机容器实验路线（不推荐生产，仅记录）

1. 安装 Docker Desktop for Apple Silicon，Settings → 勾选 *Use Rosetta for x86/amd64 emulation*。
2. `docker run --rm --platform linux/amd64 -v "$PWD/TGW-SDK_V1.0.8/Cplusplus/Redhat-7.6/c++/lib:/libs" centos:7 bash -c "ldd /libs/libtgw.so"`
   —— 观察动态链接是否完整解析。
3. 若成功，可进一步在容器内安装 python:3.11-slim amd64 镜像 + linux 版 whl 运行桥接服务。
4. 风险：Rosetta 对老 glibc 的 syscall 转译未承诺全覆盖；行情推送延迟抖动；厂商不支持该形态。
   结论仍是以方案 A 为主。
