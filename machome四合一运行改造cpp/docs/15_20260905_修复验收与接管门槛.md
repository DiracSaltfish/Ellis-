# 2026-09-05 修复验收与接管门槛

本轮完成了已复现问题的修复、包内 Upload 业务接线和本地候选包构建。**这是待现场核验的接管候选版，不能认定“完美复刻”或“周一无需核验即可直接接管”。** 原因是生产凭据、存量数据、真实行情依赖、完整交易时段与故障隔离仍有明确边界。本文不把未做的验证打勾。

本轮没有连接 machome，没有部署、停用或重启 machome 上的任何服务，也没有向生产上传端发送业务数据或提交真实 QMT 委托。所有实际进程测试使用本机临时目录、模拟数据或离线入口。

## 一、接受的实现边界

用户已明确接受“包内组件，优先保持业务等价”。UploadEngine 现在支持 `sink_mode=bundled_business`，统一监管包内的 Go 网站与 Python 业务组件。它们不使用旧部署目录、旧 venv、旧 LaunchAgent 或旧桌面 UI。网站保留原 HTTP/WS、Vue 页面、MySQL 和历史格式；四合一仍提供原生管理界面。

264 个基线源文件中 262 个逐文件 SHA-256 一致，仅两处有意适配：

- `cmd/web/main.go`：包内模式要求 MySQL 可连接，连接失败退出，避免静默变为内存服务。
- `scripts/upload_health_monitor.py`：包内运行时读取四合一实际拥有的进程状态，沿用原业务/新鲜度检查。

独立 Go/Python 业务源码位于 `app/components/upload/business`，基线清单为该目录的 `BASELINE-SHA256.json`。本轮选择保留原上传器的 IBKR 行为，包内业务模式不再并行启动另一套原生 Upload 估值/记录流水线。原生 IBKR bridge 仍可供记录模式使用。

网站业务编辑继续通过原网站完成。原生页面的 SQLite 演练编辑器在包内业务模式禁用，并提供网站入口，防止操作员把演练仓储当成实际网站数据库。

## 四、周一前必须关闭的接管条件

以下条件未完成前，结论为 **NO-GO：不要直接替换现有四服务**。

- [ ] 从实际生产导出并逐项核对配置：原 Upload 实际启用的服务/一次性回填任务与参数、认证、MySQL DSN、TGW 账户、Premium 清单与名称、Webull token/CIDR/登录配置、Wind ABI 清单和 QMT 目标。
- [ ] 对 MySQL 和各文件仓储获得一致性备份。迁移后核对行数、日期覆盖、关键基金、仓位覆盖与文件校验值。模板中的空值不是已经配好。
- [ ] 目标主机 Wind 程序与本次最终 probe 的哈希匹配有效 ABI 清单。历史批准的 manifest 不能不核对就用于新签名后的产物。
- [ ] 真实 TGW/Webull/Wind/TWS/QMT 接入与有效行情验证：关注订阅数量、时间戳、数据新鲜度、ACK、七只 ETF 的当日 PCF、网站日终写入。
- [ ] Webull 原客户端、慢客户、无 pong；Premium 真信号重连回补；PCF 真实限流/跨日；完整工作窗口与长期驻留。
- [ ] 如需保留原双击下单功能，明确启用运行时 QMT gate，并验证真实服务连接与协议同步。仅编译进能力不等于已启用交易。
- [ ] 准备逐模块交接与回滚，使用本文最终包 SHA；切换时确认旧写入者已退出后才启动新组件。网站端口预检只覆盖端口冲突，不能代替全部旧 uploader 的交接核验。

四个原生内核仍主要运行在同一 Agent 的四条线程中。Upload 的业务组件、TGW/Wind/浏览器 helper 有进程边界，但 **Agent 内部的内存破坏或崩溃仍可能影响四模块**。这与原四个独立主进程的故障隔离不等价；本轮没有把这一结构性差异判为关闭。

Premium 的观察/热清单、名称和历史沿用原 Core 文件格式，需从一致性导出复制到新 `data/premium/config` 与 `data/premium/data`；Webull 需把原 token 放入新根的 `runtime/api.token`，登录 profile 需按实际原路径迁移。不要在两个正在写入的服务间共享可写 profile 或缓存目录。
