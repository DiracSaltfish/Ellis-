## 3. 必须关闭的代码问题

以下 P1 表示阻断等价接管；P2 表示需修复或明确记录接受范围。不是所有条目都同等严重，也不是每项都应通过放开权限解决。

### U-01 / P1：Upload 不存在可启用的生产上传模式

[`UploadEngine::initialize`](../app/modules/upload/UploadEngine.cpp:1259) 只接受 `sink_mode=record_only`，其他值直接进入 `blocked`。[`recordPayload`](../app/modules/upload/UploadEngine.cpp:2338) 仅写 SQLite；[`executeJob`](../app/modules/upload/UploadEngine.cpp:2612) 随后把记录成功计作任务成功。`request`、`expected_ack` 是存入 JSON 的描述，不能当成实际发送和收到 ACK。[`upload_ack`](../app/modules/upload/UploadEngine.cpp:1482) 是命令入口，并非自动读取服务端回执的传输层。

原 Sina 实现会实际 POST、携带上传认证、处理非 2xx、解析 accepted/enabled，见 [原 uploadQuotes](/Users/ellis/newnavnav/cmd/sina-quote-uploader/main.go:154)。本次复现设置 live sink 后返回 `blocked`，错误为“当前原生 UploadEngine 仅允许 sink_mode=record_only”。

**关闭条件：** 实现真实可配置的发送/ACK 传输，与本地 fake 服务验证认证失败、超时、断线重连、重复 ACK、last-good、全量/增量及反向请求。可保持默认关闭，但必须证明在明确启用时完整工作；不能仅修改提示语或去掉初始化检查。

### U-02 / P1：采集、估值和部分日终任务缺少实际计算链路

[`executeJob`](../app/modules/upload/UploadEngine.cpp:2457) 只对五类任务调用 `collectForJob`。`sina-public` 从已存在的 `latest_quotes` 读取，而不是自主拉取 Sina；私有 uploader 从已存在的 `valuation_inputs` 取结果。IBKR 消息路径会写行情，但没有在该路径重新构造每个家族的生产输入并持续调用估值保存。估值保存主要经 [`upload_ingest_valuation`](../app/modules/upload/UploadEngine.cpp:1470) 接收已准备好的输入。

`daily-calibration`、`effective-ratio-fit` 落入 [`executeJob` 的通用记录分支](../app/modules/upload/UploadEngine.cpp:2558)，没有执行原校准/拟合算法。原校准逻辑会加载 NAV 与配对收盘、计算并 upsert calibration，见 [原 SyncMissing](/Users/ellis/newnavnav/internal/calsync/calibration.go:43)。按点触发并写成功记录，不等于原日终任务实际完成。

**关闭条件：** 用同一脱敏原始输入驱动两套程序，逐家族对比实时估值和 fallback；用至少两个连续业务日验证校准、仓位拟合、分钟重建、收盘及回填的实际数据表变化。仅注入最终估值结果或检查 run_count 不算通过。

### U-03 / P1：Upload 网站/原数据仓储未完整承接

当前 Upload 主体提供本地 SQLite 和原生页面，构建目标未包含原 Go HTTP 网站服务。[Upload 仓储初始化](../app/modules/upload/UploadEngine.cpp:2021) 创建新的 `upload.sqlite3`；网站深链仍需外部网站可用。原 Go 网站的请求路由、反向 WS 请求和数据仓储并未因有 Qt 页面而等价实现。

如果“接管 Upload”包括原常驻 web 服务，那么停止旧 web 后，四合一无法承接原 8080/网站 API。也未见覆盖四套原数据库/历史/配置的完整自动迁移和往返一致性证明。

**关闭条件：** 明确网站运行边界并兑现原范围：实现等价服务及存储迁移，或由用户明确接受继续保留网站服务这一范围变化；基金/净值/份额/仓位/历史及反向请求逐接口验证。目前不能声称已经全原生替代。

### P-01 / P1：Premium 清单保存后，重启会被覆盖

[`writeRuntimeConfiguration`](../app/modules/premium/engine/PremiumAEngine.cpp:94) 每次启动都从 `context_.settings` 或默认值写 `watchlist.json`、`l1_hotlist.json`。原生修改命令将新列表保存到文件，但不更新这份初始 settings。因此下一次启动会覆盖用户修改。

**已复现：** 初始 `159217.SZ` → UI 同等命令改为 `510300.SH` 并成功 → stop/start → 恢复 `159217.SZ`。热清单具有同样覆盖机制。证券名称文件也被重写为代码作为名称，而未保留原名称映射。

**关闭条件：** 建立唯一持久化配置来源，启动读取已保存的有效清单；加入 stop/start、Agent 重启、外部 B 客户端修改和损坏文件回退测试，确认热清单及证券名称一并保留。

### P-02 / P1：TGW helper 异常退出后没有恢复监管

[`startTgwHelper` 的 error/finished 回调](../app/modules/premium/engine/PremiumAEngine.cpp:348) 仅更新 failed/exited 和 lastError，没有安排重启。快照定时器只发状态，`start()` 又在 `running_` 为真时直接返回。Agent 本身仍活着，launchd 的 KeepAlive 不会解决这个 helper 故障。

原 [ConsoleWindow::handleFinished](/Users/ellis/工具程序开发/溢价率拉升监控cpp/src/console/ConsoleWindow.cpp:1299) 会延迟恢复，并在五分钟三次达到上限后进入 FAULT。旧监管没有随 CoreServer 一起自动迁入。

**关闭条件：** 在本地用可控 fake helper 验证异常退出恢复、依赖组顺序、退避与熔断、人工停止不复活；然后核对真实 TGW 重连和新 full 前清缓存规则。

### P-03 / P2 待验证：原生 UI 同步合同发生变化

[`publishSync`](../app/modules/premium/engine/PremiumAEngine.cpp:390) 仅发送 sync_begin、summaries、sync_complete，没有在这个同步序列中返回 Core 的近 30 分钟 signalHistory。**HubAgent/HubClient 另有关键事件审计重放，可能补回部分或全部信号，不能仅据这个函数断言 UI 一定丢失信号。** 外部 B 端仍走原 Core 协议；原生 UI 则需验证两条机制的组合效果。

**关闭条件：** Agent 已产生信号时重开 UI/重连，验证不同审计游标、清空本地页面、审计保留窗口后的实时信号回补及去重。若审计重放已满足业务等价，可记录通过而无需重复实现；本轮尚未完成这一组合测试。

### W-01 / P1：Webull 新服务只监听回环地址

[`WebullV2Server::start`](../app/modules/webull/WebullEngine.cpp:299) 写死 `QHostAddress::LocalHost`，未使用旧 `api.host` 和 CIDR 配置。原 [ApiServer](/Users/ellis/Desktop/ETF交割/WebullData/webull_lv2_gateway/src/webull_lv2_gateway/api_server.py:92) 按配置监听，基线配置 host 为 `0.0.0.0`，并有 CIDR + Bearer 校验。

**影响：** 旧局域网行情客户端不能保持原地址接入。不是仅在 UI 中填一个主机地址就能修复。

**关闭条件：** 实现可配置监听及原 CIDR/Bearer 边界，使用两个不同本地地址/测试网络验证允许和拒绝；不要只把常量改成 Any 而遗漏访问控制。

### W-02 / P2（有对应客户端时为 P1）：v1、应用心跳和慢客户合同不完整

原服务仍有 v1 compatibility + Deprecation 路由，且收到文本 `ping` 返回 JSON `pong`；新 [`consume`](../app/modules/webull/WebullEngine.cpp:353) 只保留 v1 live，收到文本帧不处理应用 ping，仅处理 RFC opcode 9。原 20 秒 RFC 心跳未保留为发送定时器，新代码只有 25 秒应用 heartbeat。

**已复现：** 同一新服务 `/v2/status` 为 200、`/v1/status` 为 404；v2 WS 成功收到 hello 后，文本 ping 300 毫秒无 pong，源码中也没有该响应分支。

此外新 [`broadcast`](../app/modules/webull/WebullEngine.cpp:323) 在 socket 积压超过 256 KiB 后跳过新帧，未保存每客户 latest-only pending、未记录原丢旧帧计数，和原每客户容量 1 队列不同。

**关闭条件：** 清点实际客户端版本及心跳习惯，保留相应协议；加入旧客户端直接连接、文本 ping、无 pong 超时、最后一帧/慢客户端恢复测试。若确实废弃 v1，应作为明确的兼容性变更记录，不能称为原样复刻。

### R-01 / P1：PCF 刷新缺少交易所级串行与间隔门禁

[`fetchNextPcf`](../app/modules/redemption/RedemptionEngine.cpp:1249) 仅判断每个 symbol 的 inFlight；第一次请求未完成时再次调用会跳过该 symbol 并请求下一只。完成回调中的延迟 8 秒不能约束其他入口；404/410 的候选 URL 切换还会立即再次发起。

**已复现：** 两次连续 `redemption_pcf_refresh`，200 毫秒内本地 fake HTTP 服务收到 2 条请求，且尚未响应任何一条。原 [refresh_pcf](/Users/ellis/Desktop/ETF交割/实时申购赎回数据/etf_monitor_server.py:1242) 有共享锁，底层 [rate_limited_fetch](/Users/ellis/Desktop/ETF交割/实时申购赎回数据/szse_pcf.py:1319) 有交易所锁、请求间隔和冷却持久化。

**关闭条件：** 单一 PCF 请求队列，所有定时/手动/候选重试共享同一交易所 gate；复验连续点击、跨分钟 tick、404 fallback、403/429/503、重启后的冷却以及每天最多尝试次数。

### R-02 / P2：通知、声音和设置仅部分迁入

不能说四合一完全没有提醒：[RealtimePage](../app/src/ui/ModulePages.cpp:1886) 会发 alertRequested，[MainWindow](../app/src/ui/MainWindow.cpp:129) 会蜂鸣/托盘提示。

但原程序的自选音频、音量、重复次数、冷却、非模态弹窗持续时间未完整迁入。原 [声音播放](/Users/ellis/Desktop/ETF交割/实时申购赎回数据/etf_remote_client.py:1842) 和 [提醒冷却](/Users/ellis/Desktop/ETF交割/实时申购赎回数据/etf_remote_client.py:2043) 有明确实现；新 UI 直接蜂鸣和固定 8 秒托盘提示。后台 [`notification_decision`](../app/modules/redemption/RedemptionEngine.cpp:562) 即使 enabled=true 也固定 sent=false/record_only=true；这是已复现的设计限制，不代表当前 UI 不响。

**关闭条件：** 对声音/弹窗/冷却/设置逐项恢复，或由业务方明确接受缩减；多标的一轮合并、重连不误报、冷却只压提示不丢历史必须有回归证据。后台外部通知若要交付，还需实际发送器与失败重试。

### R-03 / P2：申赎流量边界不足，长期驻留不能按清单判通过

[`broadcastCompat`](../app/modules/redemption/RedemptionEngine.cpp:1483) 对所有 WebSocket 直接 sendTextMessage，没有每客户发送上限或慢客户淘汰。`acceptCompatibilityConnection` 对无换行输入先 `canReadLine` 返回，再做大小判断；[`readHelperOutput`](../app/modules/redemption/RedemptionEngine.cpp:1104) 也在找到换行后才判断行长。持续无换行输入缺少已接收总 buffer 的前置上限。

**关闭条件：** 加入 bounded queue/缓冲上限、慢客户退出、无换行超长输入、正常最后帧送达和其他模块持续更新的故障测试。此项为静态确认风险，本轮没有用耗尽内存的方式压测。

### I-01 / P1：当前集成测试不能代表四个原生模块同时运行

[`modules.local-test.json`](../config/modules.local-test.json:41) 的 Premium 显式是 `legacy_probe`；Redemption 未填写 engine，按 [`ModuleConfig`](../app/src/common/Config.h:41) 默认 `legacy_probe`，走旧 RealtimeClient + mock server。Upload 目前由 startUpload 无条件进入原生引擎，Webull 配置为 native，因此并不是四个 native 的整合验收。

`full-smoke` 通过证明当前这套混合测试配置能工作，不证明新 Premium 与新 Redemption 同驻留的生命周期、控制结果和隔离。baseline-invisible 是在禁读对应旧目录后运行模块测试，不是四模块整天真实业务运行。

**关闭条件：** 新增四模块全部 native 的集成配置，用随机本地端口、临时仓储和包内 fake helper，断言实际上报的 engine identity；覆盖全局模式、单模块重启、GUI 重连、队列压力和持续运行。

## 5. 建议的关闭顺序与周一安排

1. **周一维持四个独立服务。** 本轮不做任何机器切换。原会话提及 Premium 控制台不是 LaunchAgent，若之后主机重启/注销需另行确认控制台；本轮没有重新检查或改动它。
2. 首先补齐 Upload 业务本体：发送/ACK、自主输入、家族估值流水线、校准/拟合、网站范围和存储迁移。这些是实现工作，不是周一切换前临时开权限能解决的问题。
3. 修 Premium 清单持久化、helper 监管与 UI 同步；修 Webull 网络/协议；修 PCF 全局 gate 和申赎队列，恢复必要提醒设置。
4. 建立四 native 集成配置，并把本次缺口转为“修复后期望相反”的正式回归断言。本次复现程序退出 0 仅表示缺口仍存在，不能原封不动作为修复通过测试。
5. 冻结代码/配置/候选包后先完成本地同输入差分及长稳，再安排另行授权的真实时段验证与逐模块切换。真实 QMT 下单是否纳入首轮范围需明确，不应在代码验收时擅自放开。

**当前应使用的交付描述：四原生引擎已建立、部分核心迁移和本地测试通过，仍有明确业务缺口的整合开发候选版。不能使用“完美复刻”“四模块全部验收完成”“周一可直接替换”。**
