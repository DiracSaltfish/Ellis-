# CPPUI B 端与本地 IOPV 协同迭代方案

> 2026-09-09 用户补充确认：实际 Backend V10 已支持 ETF 申赎。后续实现以此为基线；原文 9.9 附带脚本结论仅是历史源码评估，不能用来判定 V10 不支持。V32 候选实现和验收记录位于 UI_V32_拉涨监控改造/docs/V32_本地IOPV_迭代与验收.md。

评估日期：2026-09-09。范围：UI_V31 源码、五合一 v1.1 本地 IOPV/A 端源码。仅静态评估和方案，没有修改客户端或服务代码，没有连接实际交易账户或发送交易。本次不以源码存在代替真实 Backend 版本验收。

## 建议分工

网页承担分时估值、历史查询、成分与质量检查；A 端负责 PCF、报价汇聚、本地估值和拉涨信号；B 端作为轻量操作终端，只收简要信号和已打开标的的估值/盘口，直接对接既有 QMT Backend 完成申赎、订单查询、卖出和撤单。网页不承担下单；B 不下载全成分、不重算 IOPV、不复制分钟数据库。

优先完成：新版估值/信号合同和交易能力核验，同时加入代码直达；不要只在旧列表顶部加搜索框后就宣布兼容新 IOPV。

## 核实的现状与缺口

| 项目 | 当前实现 | 迭代要求 |
|---|---|---|
| 快捷进入 | PullMonitorWindow 主要双击信号/快照行；Coordinator::openDetail 要求 monitorWindow_ 已存在。相同标的复用窗口，默认最多 4 个详情 | 独立入口自动准备监控 UI 会话，然后打开/激活详情；没有拉涨信号也可进入 |
| 代码格式 | normalizePullMonitorSymbol 接受六位代码及 513090.SH；不接受 SH513090 | 统一支持六位、交易所前缀和后缀；通过目录核实名称、市场和能力，不能把任意六位数字当 ETF |
| B 行情协议 | Worker 连接 /ws/v2/summary 和 /ws/v2/detail；Snapshot 只有 iopvE6、旧溢价字段 | 引入明确的本地估值对象，区分 exchange_iopv 与 local_iopv，不能悄悄改旧字段语义 |
| 新信号接收 | A 本地信号仅广播到 /ws/v3/local-iopv-signals；旧 v2 同步也跳过 local_pcf 信号。B 目前只处理 type=signal | 新 B 必须接新通道，正确识别 local_iopv_signal；否则“行情能看见但新信号收不到” |
| 新信号可靠性 | v3 目前只 hello + 实时推送，未实现该通道的 sync/resume/补发处理。A 有信号持久化，但不能等同于客户端可恢复 | 实现会话、游标、补发、缺口告知与去重；补发不得再次触发实时声音 |
| A 详情覆盖 | v2 subscribe 校验格式并 ACK，但不保证已在监控清单；持续详情广播受 fixedSymbols_ 限制 | ACK 要分别表明请求接受、行情订阅完成、本地估值可用。目录清楚区分 monitored/valuation_supported/quote_supported；必要时增加临时详情订阅，不擅自加入永久信号监控 |
| 估值可用性 | Go 的 eligible_for_signal 同时受结算模型影响；A midpoint 逻辑另有独立判断，允许结算不可用但中间价可用 | A 对外返回按 basis 的 allowed/reasons。B 不直接把总 eligible 当中间价门禁，否则会与 A 不一致 |
| 申赎 | Coordinator 和 Controller 限定 QMT1/2；qty 固定 1，模型校验也限定 1；双击发送 | 第一版继续一篮子，展示当日每篮份额及账户；多篮子需要 Backend 合同支持后再扩展 |
| 申赎 Backend | sendEtfOrder 验证请求和 TCP；存在协议就绪字段，但此发送路径不强制检查它。就绪文案指向 Backend 10.1 push_sync；附带 9.9 普通脚本未找到 etf_order 分支 | 核实实际运行 Backend，握手显式返回 etf_order/action/quantity_unit/幂等/查询能力；不能只根据 TCP 已连接或版本文案开放 |
| 请求未知态 | 10 秒防重锁超时后释放并查询，不自动重发；再次手工提交产生新 ID | 持久化未知请求，通过 client_order_id 对账后决定解除；超时不等于失败或未下单 |
| 卖出默认行为 | 支持买一快卖/限价卖出；默认 100000 股；断线、过期、Replay、持仓未知按当前设计仅警告 | 保留原手工操作习惯作为明确可选策略；默认快卖建议要求实时盘口与已知可卖量，缓存手工限价独立呈现；Replay 页面不能混淆实盘操作 |
| 订单结果 | 代码已区分“提交给 QMT”和成交，已有委托/持仓同步、撤单、client_order_id | 进一步连接申赎请求→Backend 接收→QMT 委托→成交/拒绝/撤单→持仓确认，不把 etf_order_result.success 当作交易所成功 |

## 1. 快捷操作入口

监控窗口顶部固定“输入代码 / 名称 → 打开”；主交易窗口菜单和应用内快捷键 Cmd/Ctrl+K 打开同一选择器。支持 513090、513090.SH、SH513090；优先精确代码匹配，再名称搜索。回车只打开，不发送订单；错误、非 ETF、未覆盖本地估值均给出可理解的结果。

打开后立即显示代码、名称、账户，盘口/IOPV 加载独立显示。不要因为没有信号、没有 PCF 或 IOPV 缺失而阻止查看持仓和订单；是否可以执行某种交易动作另行判断。相同代码激活已有窗口；满 4 个时让用户选择复用，不静默关闭有未决订单的窗口。

可复用最近打开/收藏。第二阶段再增加网页“在 CPPUI 打开”：自定义 URL（例如 qmtui://open?symbol=513090.SH）只传标的，处理单实例转发、macOS/Windows 注册与用户点击。链接不可携带可执行的订单、账号、数量或价格；导航不能直接下单。先完成输入代码和复制代码即可解决主要障碍。

## 2. A/B 最小数据合同

以下为建议接口，尚未实现，需先共同定稿。保留旧 19195 L1 和 v2 协议，新增完整版本通道而非改变旧协议。

- symbol_directory：代码、名称、市场、是否 ETF、本地估值覆盖、是否参与拉涨监控、PCF 日期/单位、可用接口能力。低频取全量并按版本更新。仅可估值不代表可申赎；可交易能力最终由 Backend/产品规则决定。
- signal stream：hello 中说明 schema、server_session、trade_date、basis 与恢复能力；事件含 event_id/sequence/symbol/model/time、触发时的 IOPV/溢价/涨幅和质量版本；支持 resume(cursor)、完整同步和 gap。换日、A 重启或口径变更重新初始化，不沿用昨日缓存。
- selected-symbol valuation：只订阅打开的 1–4 个标的；首次全量、后续最新值覆盖。包含 midpoint、settlement_buy、settlement_sell 及对应 FX，SH/SZ 渠道、PCF hash/unit、calculated_at、quote_at、source_session、版本、每口径 gate/reasons。数量、价格、百分比单位在 schema 中固定，不把 null 解析成 0。
- 原盘口/最新价继续使用现有明确定义的行情协议；A 返回或附带所用行情时间，B 避免拿新价格与旧 NAV 混算后标为当前溢价。股/手展示转换留在 UI，API 股数不变。B 现有 E6 价格、PPM 溢价、E2 量字段与 Go 的浮点价格/百分数必须显式转换并测边界。
- B 不需要拉 /minutes、/components 或全量每 3 秒 SSE；这些保留给网页。当前 Go /snapshots 和 SSE 均为全量，不能直接当作最终轻量 B 接口。

状态分别表达“无数据、等待 PCF、停牌待核实、已确认停牌、成分陈旧、结算模型仅参考、断线、回放”。不要仅显示绿色连接图标或一把统一交易锁。IOPV 观察质量与 Backend 是否允许普通手工交易是不同概念。

## 3. B 交易详情的最小布局

顶部：代码+名称、QMT1/QMT2 账户标签、行情状态、估值时间、当前信号计算口径。

主体：必要的五档/十档盘口、两种本地估值及买卖结算情景，触发信号快照与当前快照分开；不放完整分时图。快捷按钮“网页查看”打开该基金。

操作：一篮子申购/赎回显示实际每篮份额，卖出数量与价格、可卖持仓、订单列表与撤单。申赎篮子单位不可直接用盘口“手”代替；现有卖出仍以股为协议单位。

订单持续可查：窗口关闭/标的移出监控不能清除未决交易；下次打开恢复。写入审计包括账户、操作、数量单位、请求 ID、当时 NAV 口径/PCF hash/行情时间和 Backend 结果。审计不得包含凭据。

## 分期交付与验收

1. **P0 合同与关键闭环**：清点实际 Backend 能力；定义本地估值/信号合同与 A/B 门禁一致性；修复未知请求防重设计。并行范围是工作分解建议，不要求当前启动额外任务。
2. **V32.0 最小可用版**：复制 V31 为独立新目录/应用标识，增加代码直达；接 A 新估值与可靠信号；保留 QMT1/2 一篮子、原订单查询卖出撤单；不迁移历史图和全成分到 B。旧版安装与配置可回退。
3. **V32.1 效率增强**：网页唤起、最近/收藏、订单未决恢复与审计检索、能力展示和清晰错误处理。
4. **后续可选**：多篮子、自定义信号口径、更多账户。必须分别核实 Backend 及产品规则，不能因主 UI 已有 QMT3/5 就自动开放申赎路由。

验收用离线 mock A + mock Backend，先不连接实盘：
- 无信号代码也能打开；前后缀/无效代码；重复打开；4 窗口限制；监控关闭再导航；不会产生下单请求。
- 本地/交易所 NAV 不混用；缺失值与价格/量/PPM 单位；SH/SZ 路由；同 basis 与网页一致；中间价有效但结算不可用时仍正确展示。
- 断线重连、A 重启、零点换日、PCF 修订、乱序/重复/丢事件；补发不响铃、不触发任何交易。
- Backend 不支持申赎/未完成同步；一篮子单位；延迟 ACK、10 秒超时、重启恢复；同请求重试不重复执行；已接受但未成交的展示。
- 多账户隔离、未知持仓与缓存价策略；成交/拒绝/撤单/持仓对账。
- A 的 L1/v2 原客户端无回归；B 关闭详情即释放其临时订阅；高频行情不阻塞 UI，不下载网页全量历史。

真实联调前单列“实际 Backend 版本、etf_order 能力、qty 单位和去重保证”的证明。当前评估不能确认服务器实际安装的后端脚本与目录附带 9.9 是否相同，也未验证真实申赎业务回报。
