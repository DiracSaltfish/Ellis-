## 原型实现

一次载入模块后，由进程内队列管理订阅，主队列每 200 毫秒最多处理一项增删操作，回调按订阅 ID 映射标的。导出在独立串行队列执行，每秒只写发生变化的最新缓存，不再附加调试器。控制文件原子替换、标的去重且限 97 只、单帧大小限制、30 秒租约失效退订均包含在原型内。

两条 SQL 均使用 LATENCY(60000 MS)，仅选择 etfbuynumber、etfbuyamount、etfbuymoney、etfsellnumber、etfsellamount、etfsellmoney 六项字段；本次新增订阅不包含报价字段。Wind 自身行情页面保持打开，其固有负载包含在基线中。

## 异常及限制

- 两次前置初始化尝试由于全局 Java 模块为空返回 -5，未建立订阅。成功版本使用独立回调上下文；因此“1 次初始化”指成功方案的一轮运行，整个排查还包括两次失败的调试器附加。
- 离线检查还发现旧初始化参数中空日志路径的风险。原型依赖当前 Wind 私有 ABI，不可跨版本直接使用；量产必须核验 Wind 和 TBAPI 二进制版本及布局。
- 重加 48 只期间 CPU 曾到 84.5%，后续 RSS 峰值 507.1 MiB，退订后观察期仍约 431.6 MiB。主队列最大排队延迟 1.272 秒。不能凭这一轮判断是内存泄漏或全由订阅造成，也不能宣称完全无 UI 卡顿；需要多轮增删与长时间测试。
- 7 只出现第二次回调，但本次未同步记录上游实际变化时刻，也未保留所有回调的逐帧内容，不能据此证明每只真实变动一分钟内送达。LATENCY 设置与实际服务端推送延迟必须分开验证。
- 97 只六字段都通过现有 helper 的 fixture 解码器校验。首次检查发现原型输出带小数的毫秒时间戳，Qt toInteger 读为零；已将原型改为 int64 输出并编译通过，在副本上规范时间戳后解码验证通过。性能测试对应 probe-tested.mm；修正版 probe-timestamp-fixed.mm 未再次注入运行。时间戳表示接收时间，不代表交易日。
- 每秒进程状态采样只能说明未观察到暂停；主队列心跳是响应性指标，不能替代人工交互/完整 UI 延迟测试。
