# 五合一 1.1.1 内置批量订阅升级

一次初始化后，订阅增删与导出全部留在 Wind 进程内执行。首选部署参数：旧池 500 毫秒（延续旧 SQL 实际值），港股通池 5000 毫秒。网页数据刷新仍沿用现有节流和按变化重绘逻辑。

## 内置方案

- 包内新增 wind_batch_probe.mm，共享一个回调上下文，按 sub_id 映射标的；在 Wind 主队列每 100 毫秒最多处理一项订阅操作，最多一个排队任务。查询只包含六项申赎字段，不增加行情字段。
- 独立串行队列每 250 毫秒导出有变化的缓存；主程序 helper 每秒取文件。文件原子替换，写入失败不清除脏标记，下次重试。
- helper 保留原协议，旧池接口、旧池提醒、原生页面、港股通私有网页都可继续使用。旧池 7 只与港股通池 97 只由同一个管理器维护，总计 104 只。
- 同一 Wind 进程内可停订、恢复、追加和 helper 重启接管，无须重新附加 LLDB。Wind 正常重启后才重新初始化。无法确认已有管理器状态时拒绝重复加载，提示正常重启 Wind。
- 控制器互斥锁阻止多个 helper 同时控制；校验 Wind、TBAPI、旧探针、新探针 SHA256。每秒续约，30 秒失联后逐项退订。进程 ID、实例 ID、订阅 ID 三重匹配防止读取旧缓存。
- 单帧大小限制、订阅数上限 256、管理操作记录最多保留约 256 条。异常不会触发无限重试初始化，也不会 SIGKILL Wind。

## 本机验证

正式 helper 端到端测试：首次旧池就绪 7.61 秒，追加港股通 97 只 10.28 秒。104 只均通过真实数据解码，频率分别为 500 / 5000 毫秒。稳定观察 60 秒：CPU 中位数 9.7%、最大 28.9%，RSS 峰值 346.5 MiB，主队列最大排队延迟约 25.35 毫秒。初始化之后每秒进程采样未观察到暂停状态。

重复追加验证订阅 ID 不变；全部退订、恢复订阅均通过。终止一次性测试 helper 后约 31.16 秒自动清空订阅，启动新 helper 成功复用同一个 Wind 内管理器。最终本机测试订阅为 0。

频率比较额外测试了 60 秒、5 秒、1 秒，每组 97 只观察 90 秒；都可建立订阅且没有 Wind 回调错误码。观察期自然更新很少：分别 0、0、1 次新增回调，不能据此承诺高密度更新吞吐量或推送延迟上限。因此生产采用 5 秒，不把 1 秒空闲测试解释为满负载性能保证。

本次定位到 159742.SZ 返回两条完全相同的记录。解码器现在接受完全一致的重复行，仅保留一条；内容冲突、截断、零行均拒绝。修复后本机全量 104 只可正常解析。

四项回归全部通过：redemption-engine、redemption-baseline-invisible、redemption-wind-helper、wind-batch-decode。
