# Wind 本机低频订阅性能测试

范围：只在本机测试，machome 港股通池持续禁用。使用同一份97只清单，查询6个申赎字段，不订阅价格和盘口。用户接受逐标的约一分钟延迟。

## 已定位的实现问题

1. 生产探针验证了传入的 latency_ms 范围，却在创建与修改SQL时均写死 LATENCY(500 MS)。网页刷新频率与Wind订阅频率是两层设置。
2. 生产helper每新增一只都会启动LLDB附加Wind，再加载独立探针库、调用创建订阅，最后detach。暂停由采集器采用的调试器注入方式造成。
3. 稳定回调在Wind进程中写出文件；采集器读取文件不需要暂停Wind。因此“导出数据必须暂停”不成立，暂停集中在初始化、订阅管理和停订阶段。

## 测试方法与限制

单只500ms、单只60000ms、10/30/97只60000ms分别观察约75秒，以1秒间隔采样ps CPU、RSS和进程状态，记录每次LLDB调用耗时和回调序号。LLDB总调用耗时包含附加、表达式编译/执行与分离，不能全部算成精确的停顿时长；进程状态T采样仅表示捕获到暂停状态的样本数。

本机与machome的Wind主程序和TBAPI2库SHA256一致。首次预检遇到EXC_BAD_ACCESS，停订函数返回0且Wind已detach；第二轮采用独立优化构建的探针，去掉尚未初始化时自行调用CJAVAInit的回退路径，再进行分档测试。由于同时存在初始化时间与构建变化，首次异常的准确根因尚未定位，不能将它算作订阅数量导致的故障。

所有原型仅存放在测试目录，未替换生产探针。SQL中的60秒参数已获正常返回与初始数据，不等于已验证自然变化的最大端到端延迟。测试不覆盖长时间运行、其他Wind页面负载或500ms下97只的稳定负载。

## 修复方向

- 优先减少LLDB附加次数：一次加载后，在Wind进程内通过受控命令队列管理新池订阅，验证正确线程和线程安全性。
- 使用真正生效的60秒参数，进一步验证批量查询是否支持以及变动回调时延。
- 一分钟的数据文件刷新可以在回调/采集层实现，不需要每分钟重新附加调试器。
- 旧7只维持原采集与提醒策略，新池继续隔离并保持关闭。完全免调试器暂停需要Wind支持的正式接口或加载机制，当前注入路径不能承诺。
