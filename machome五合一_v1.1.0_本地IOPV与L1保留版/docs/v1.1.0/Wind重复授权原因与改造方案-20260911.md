# Wind 重复授权原因与五合一改造方案

核查日期：2026-09-11，约 14:07–14:15，Asia/Shanghai。通过 ssh machome 只读核查进程、launchd、签名、TCC 授权记录和系统日志；对照本地五合一及独立版源码。本轮只新增本文，不改生产程序、权限、订阅或 Wind 状态。

## 结论

补充核对：machome 的 sw_vers 实际返回 macOS 26.6（25G72），不是 27。用户补充观察到“同一签名每次启动也提示”，应将启动/会话相关的重新授权作为独立验收场景。稳定签名只处理升级身份问题，不保证普通 App 数据弹窗的允许决定跨启动永久有效；目前未找到足以证明此机器适用“每次启动必问”统一规则的 Apple 文档。应保持同一二进制，先对照完全磁盘访问开关与真实进程链，再分别测试请求方和 Wind 重启，避免同时改变多个变量。

最直接的差异是：独立版具有完全磁盘访问授权，五合一没有。五合一访问 Wind 容器时被 macOS 归为另一个应用身份，不能沿用独立版授权。现场证据不支持“整个五合一每天退出重启导致重新授权”。Wind 本身按日关闭重开会重新经过数据访问/调试步骤，但不是独立版与五合一差异的充分解释。

尚未取得每天早晨弹窗的原文及对应完整日志，不能把每一次弹窗都认定为同一种权限，也不能断言每日授权记录为何重新创建。当前证据强烈支持优先修复其他 App 数据访问权限，其次处理升级后的签名身份延续。

## 源码解释

1. app/helpers/wind_probe/main.cpp:354 的 rawDirectory 将临时探针和采集输出放在 ~/Library/Containers/com.windin.mac.free/Data/tmp/machome-hub-probe。订阅、文件轮询和退出清理都可能接触此目录。Wind 有沙盒约束，不能简单把目录移到 Hub 数据目录后假定 Wind 仍能写入。
2. 同文件 runLldb（约 311 行）每次创建临时 LLDB 子进程，使用 /usr/bin/lldb；独立版 _run_lldb 同样是每次启动子进程，使用 /Library/Developer/CommandLineTools/usr/bin/lldb。machome 的 xcode-select 已指向 CommandLineTools，这个入口差异需记录实际工具版本验证，但不是已证实根因。
3. app/modules/redemption/RedemptionEngine.cpp:770 的 evaluateSchedule 在 09:10 启动 Wind，09:15:05 预热、09:15:30 监控，运行窗口外停订、关闭 Wind、清理探针。Agent 和 helper 保留。
4. 独立版 etf_monitor_server.py 也有 Wind 自动启动、收盘退出与清理，并不是天然让 Wind 永不退出。因此“保住五合一进程”不足以解释或解决当前差异。
5. app/scripts/build-release.sh:349 使用 --force --deep --sign -。相同 Bundle ID 并不保证重新构建后身份要求相同。

## 推荐改造顺序

### P0：先修复当前授权差异

在 machome 本机或远程桌面进入系统设置 → 隐私与安全性 → 完全磁盘访问，添加并启用实际部署包：

`/Users/ellis/Applications/Machome 四合一运行中心.app`

虽然界面已经叫五合一，部署包仍沿用“四合一”名称；不要选开发目录、候选包或旧 ETF监控主机。按系统要求在维护时段重新启动对应服务，并通过实际 launchd 进程链验证；SSH 终端读写成功不能替代生产 helper 的授权验证。若系统实际归属与本次不同，再按日志定位 Agent/helper，不盲目给多个程序追加权限。

这是需要用户在系统设置中明确授予的权限，程序内不能自行合法完成。此轮未执行授权或重启。完全磁盘访问范围较广，但它正是现场独立版已有、五合一缺失的条件。

先保留现有 Wind 日开日关策略做对照验证。若此步消除弹窗，无需为权限问题改成永久保留 Wind。

### P1：稳定签名和部署身份

- 正式构建新增签名 identity 参数；使用固定 Developer ID Application 身份，保持主 App、Agent、helper 的 Bundle/签名标识与安装位置稳定。开发版仍可 ad-hoc，明确不保证升级后授权延续。
- 按嵌套依赖顺序签名 dylib/helper/Agent，最后签 App；发布检查签名有效性及 designated requirement。不要只检查“codesign 能通过”。
- 首次从 ad-hoc 迁移到正式签名需要重新验证并可能重新授权，此后仍以升级实测为准。
- 保持原 launchd label 和包路径。更新前准备回滚包，更新后验证当前运行进程确实来自当前包，避免原地覆盖造成运行代码与磁盘签名不一致。

### P1：明确权限故障与常驻恢复状态

- helper 区分 container_access_denied、debug_attach_denied、abi_mismatch、wind_not_running、tbapi_not_ready，保留操作阶段和系统错误。禁止使用“ABI 状态”概括所有阻塞。
- 遇到明确权限拒绝进入 permission_required；抑制自动反复附加/重建目录造成弹窗循环。用户完成授权后显式重试；正常状态查询只查缓存/进程，不持续触碰受保护目录。
- 状态页增加 Agent/helper/Wind 的 PID、启动时间、签名标识、最近失败阶段、业务数据时间、最近订阅结果；无权限、未启动、没有新数据分别展示。
- 权限探测通过实际 helper 单次执行，不以 SSH 账户或读取 TCC 数据库作为产品运行时的权限判断接口。
- 调度依据 Wind 实际存活状态恢复。本地代码 windLaunchDay_==day 后不再走自动启动分支，应增加同日异常退出后的退避重启能力；权限/ABI 错误时不能盲目重启。
- 不因授权故障清空原始采集、历史数据库或已知订阅；针对不确定停订保持现有保护。

### P2：可选的 Wind 常驻模式

只有在权限修复后仍有启动成本或可靠性需求时再增加 wind_lifecycle_mode：scheduled_restart / resident。resident 模式收盘停订、停轮询，保留 Wind、Agent/helper；次日校验进程、ABI、登录和 TBAPI 后建立新订阅。不能沿用旧交易日订阅 ID、份额基线或旧捕获文件。

保留用户显式“关闭 Wind 并清理”操作。Wind 未退出时不执行退出清理，也不无限制造临时 dylib；需要设计可复用探针会话或有界的载入策略，并观察内存。常驻模式只能减少启动和附加触发点，不能替代文件权限或跨版本身份稳定性。

当前 helper 已经与业务引擎隔离，优先完成以上修改。独立 LaunchAgent 或 broker 属于后续隔离升级影响的架构选项，不作为当前重复授权的必要修复。

## 验收与回滚

1. 不改二进制，补齐授权后，从真实 launchd 链路验证 Wind 容器访问、ABI 就绪、预热、七标的订阅及数据时间推进。
2. 连续至少两个工作日覆盖收盘停订/退出、次日启动和预热；无手动授权，保留阶段日志。测试整个 Agent 保持同 PID，并单独记录 Wind PID 变化。
3. 维护时段分别验证 helper 重启、Agent 重启、Wind 同日退出后恢复；每种情况检查没有重复订阅且 6787 协议正常。
4. 正式签名迁移后验证一次跨版本升级；单次重启成功不等于升级免授权。
5. UI 关闭、正常锁屏与 macOS 重启后重新登录分别验收；图形 Wind 依赖用户 GUI 会话，不能承诺 FileVault 解锁前或无人登录时采集。
6. 自动化回归使用文件拒绝、调试拒绝、ABI 不匹配和跨日模拟，不对生产 Wind 做测试注入；不得触发 QMT 交易。
7. 回滚保留配置、业务数据库和旧完整应用包。签名身份回滚后也重新检查权限有效性。
