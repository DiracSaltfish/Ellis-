## 问题与建议

### 1. P2：V12 已连接时“获取快照”请求被服务端忽略

客户端 `src/integration/EtfMonitorClient.cpp:207` 在 WebSocket 已连接时发送 `{"type":"get_snapshot"}`，随后直接 return，不走 HTTP 回退。服务端 `app/modules/redemption/RedemptionEngine.cpp:1569` 的文本消息处理器仅比较原始字符串是否等于 `ping`，没有 get_snapshot 分支。

因此初次连接可以成功得到服务端主动快照，盘中数据变化也会触发主动推送，但点击获取快照本身不会获得对应响应。在数据静止时尤其容易误以为刷新已经完成。建议在四合一兼容端解析 JSON 并支持 get_snapshot，返回当前只读快照；保留初次连接主动快照行为。

### 2. P2：JSON 心跳无应答，客户端缺少存活超时检测

客户端 `EtfMonitorClient.cpp:216` 默认每 15 秒发送 `{"type":"ping"}`；服务端只响应纯文本 `ping`，这两个报文不相等。客户端虽然处理 pong/heartbeat，却没有根据最近收包时间或 pong 超时执行断线重连。服务端该兼容 WS 也未找到周期性 heartbeat 的发送实现。

这不代表一连接就会断开：snapshot/change/status 仍可正常送达，正常 socket 错误和断开也会触发客户端重连。但在网络黑洞、半开连接等情况下，可能持续显示已连接，缺少及时的应用层失联判断。建议服务端兼容 JSON ping（同时保留旧纯文本 ping），客户端添加带合理阈值的存活检测。不要用“是否有份额变化”代替心跳，否则休市或盘中静止会被误判。

### 3. P2：测试回放标记被 V12 丢弃，可产生实盘样式告警

服务端 `RedemptionEngine.cpp:593` 发出的 change 带 replay；`RedemptionEngine.cpp:1083` 的 fixture 注入路径在 test_mode 开启时以 replay=true 调用采集处理。

客户端 `src/models/EtfMonitorModels.cpp:421` 的 change 解析没有保存 replay；`src/application/EtfMonitorCoordinator.cpp:266` 对收到的变化直接生成横幅并播放提示音。本地纯解析验证已确认：同一个事件分别设置 replay=false/true，客户端得到完全相同、非空的告警文本。

影响有条件：目前正常 Wind 实盘接入传 replay=false，该缺陷不等于正在把实盘数据误判；只有回放/测试数据进入该连接才涉及混淆。建议保留并传递 replay，回放更新显示时加标记，禁止当作实时变化发声。不能把四合一自己的通知关闭设置理解为一定能关闭这个独立客户端的本地提示。

### 4. P3：PCF 详情缺少动态展示上下文

服务端 `/api/v1/pcf/<symbol>` 返回保存的 PCF 对象，没有合并对应标的的 custom_name、name 和当前 opportunity；而 V12 `src/models/EtfMonitorModels.cpp:514` 和 `src/presentation/EtfPcfDetailDialog.cpp:373` 支持显示这些字段。此次保存的 7 份 PCF 均没有这三个字段。

不会导致 PCF 解析失败，基金名可以回退到 fund_name，成分、篮子单位和限额仍能显示；但详情可能缺少主表已有的自定义名称和机会说明。建议在只读详情响应组装时合并当前标的上下文，不要把动态机会固化进 PCF 文件。另：未就绪 PCF 返回 404，而客户端旧协议文档写 422；现客户端统一按 HTTP 错误处理，所以这处状态码差异不是阻断点。
