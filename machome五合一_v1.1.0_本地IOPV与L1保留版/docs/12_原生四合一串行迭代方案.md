# 12 原生四合一串行迭代方案

> 派发方式已收敛为四个模块任务。2026-09-04 经用户明确调整为模块并行、完成后由主 Agent 统一整合审查；本文中的 `G/P/U/W/R/I` 编号仅作为模块内部及最终审查的检查清单，不再单独派发。权威派发清单见 [`plans/four-module-serial-work-packages.yaml`](../plans/four-module-serial-work-packages.yaml)。

## 1. 本方案解决什么问题

当前版本已经有统一 Qt UI、Hub Agent、四个 ModuleWorker 线程、控制审计、状态归一化、较完整的四个模块页面，以及原生 IBKR 行情桥；但四个 ModuleWorker 运行的主要是客户端/适配器，不是完整业务引擎。生产配置仍是：

| 模块 | 当前形态 | 与目标的差距 |
|---|---|---|
| Upload | `UploadClient` 读取 8080 和旧健康文件；原生 IBKR bridge 只负责行情 | Go 网站、定时任务、各估值/上传器、存储和全部业务页面尚未成为四合一内部能力 |
| 溢价率 A 端 | `PremiumClient` 连接外部 8421/19195；生产为 `shadow` | CoreServer、SignalEngine、持久化、TGW 接入和 A 端运行管理仍在旧部署中 |
| Webull | `WebullClient` 连接 18765；owner runner 从旧 Webull 源目录 import 业务代码 | 浏览器采集、规范化、存储、API 和调度尚未作为四合一自带组件交付 |
| 实时申赎 | `RealtimeClient` 连接 6787；owner 直接执行旧 `ETFMonitorHost` | MonitorEngine、Wind、PCF、历史、通知和服务端尚未迁入新产品 |

目标不是继续包装旧 App，而是交付一个自包含的“四合一产品”：

- 用户操作全部进入当前 Qt 原生 UI；
- 四个业务域在 Hub Agent 中各有独立 `QThread` 和明确的 `IModuleEngine`；
- 不执行、不 import、不动态链接四个旧程序目录中的任何文件；
- 不加载四个旧 LaunchAgent；
- 业务数据写入新的 MachomeHub 数据目录，不写旧程序目录；
- 必须保留外部消费者依赖的兼容协议，例如 Premium B 端使用的 8421/19195；
- 溢价率只迁 A 端服务端和 A 端运维 UI，B 端客户端及其交易能力明确排除。

## 2. “直接做进四合一”的技术定义

建议把“一个产品”和“只有一个 Unix 进程”分开。最终主结构为：

```text
Machome 四合一运行中心.app
├── UI：machome-hub-ui（Qt Widgets）
└── Agent：machome-hub-agent（Qt Core，launchd 常驻）
    ├── GlobalCoordinator / Scheduler / Audit / CredentialStore
    ├── UploadEngine QThread
    ├── PremiumAEngine QThread
    ├── WebullEngine QThread
    └── RedemptionEngine QThread
```

下列不可信或阻塞边界允许使用**四合一包内自带、无 UI、无独立配置所有权**的 helper：

- Webull Browser Helper：驱动 Chrome/WebTrade；
- Wind Probe Helper：执行私有 ABI/LLDB 探测；
- Premium TGW Helper：隔离专有行情 SDK 的阻塞调用或原生崩溃。

这些 helper 必须位于 `.app/Contents/Helpers`，由 Agent 用固定绝对包内路径和固定参数启动，只通过 owner-only Unix socket 通信。它们不是旧独立程序，不能从旧源码/Applications 目录 import 或执行文件，也不能有自己的 LaunchAgent。除这些硬件/浏览器接入边界外，调度、业务状态机、计算、持久化、通知、兼容服务和 UI 都在四合一代码库中。

强行把 Python/PyQt、Chrome、Wind 私有探针、TGW SDK 与四个 C++ 引擎塞入同一个地址空间，会形成双 Qt event loop、GIL、ABI 和崩溃扩散问题；不把“单进程”作为验收条件。验收条件是“自包含、无旧程序依赖、一个产品统一拥有生命周期”。

### 3.1 禁止写入或作为运行时依赖

可以只读分析和生成哈希；需要复用的逻辑应复制到本工程的新命名空间，并记录来源文件、源哈希、复制日期和后续改动。禁止用 symlink、运行时 `PYTHONPATH`、动态库搜索路径或配置路径把依赖重新指回旧目录。

### 3.2 开发与生产隔离

- 在四模块全部达到集成门槛前，只做本机 fixture/replay 和明确的无副作用真端点测试；
- 不自动安装或加载 machome 新版本；
- 不修改旧 plist、旧配置、旧数据、旧 token、旧日志；
- 新数据根目录固定为 `~/Library/Application Support/MachomeHub/data/<module>`；
- 导入旧数据只能“只读源、复制到新目录、校验后原子启用”，不得原地迁移；
- 四合一构建默认 `legacy_execution_allowed=false`，不存在自动回落到旧程序的路径。

### 3.3 构建期和运行期门禁

每次 Release 必须执行：

1. 扫描源码、配置、plist、Mach-O、Python import 和 app bundle，拒绝上述旧绝对路径；
2. 扫描 `ProgramArguments`，只允许包内 helper、系统工具和明确批准的外部厂商程序；
3. 启动测试记录所有 child process，发现旧二进制或旧 label 立即失败；
4. 在四个旧目录临时不可见的隔离环境中运行完整测试；
5. 断言应用退出/重启不会修改旧目录 inode、mtime 或内容哈希。

外部厂商依赖 TWS/IB Gateway、Chrome、Wind 金融终端、QMT 服务不属于“四个旧程序”，但必须通过明确 allowlist 和 adapter 接入。

## 4. 总体基础阶段（必须先串行完成）

### G-00 基线冻结与可回放语料

**工作**

- 为四个旧工程生成只读源码清单、配置结构清单和哈希 manifest；配置只保存结构与脱敏值；
- 收集旧程序的输入/输出 golden corpus：行情帧、PCF、估值结果、信号、上传 body/ACK、状态、历史文件和通知决策；
- 建立 `fixtures/<module>`，敏感字段匿名化；
- 为每个 corpus 写 provenance、时区、交易阶段和预期结果。

**完成条件**

- fixture 测试不需启动任何旧程序；
- 每个重要分支至少包含正常、空数据、陈旧、断线、边界时间和损坏输入；
- manifest 工具只读运行，测试证明不会改变源目录。

### G-01 原生模块运行时接口

新增稳定接口，替换 adapter 与外部服务强绑定：

```cpp
class IModuleEngine : public QObject {
    Q_OBJECT
public slots:
    virtual void initialize(const ModuleContext &) = 0;
    virtual void start() = 0;
    virtual void stop(StopMode) = 0;
    virtual void submit(const ModuleCommand &) = 0;
signals:
    void snapshotReady(ModuleSnapshot);
    void eventReady(ModuleEvent);
    void commandFinished(ModuleCommandResult);
};
```

`ModuleContext` 只提供受限服务：Clock、Scheduler、Network、Storage、Credential、Notification、Audit 和 bounded executor。模块不得直接获取 UI 对象、全局线程池或任意 shell。

**完成条件**

- 四个 mock engine 同时运行，任一 engine 超时不会阻塞其他模块/UI；
- 生命周期具备 initialize/start/warm/active/scheduled-idle/degraded/stop 状态；
- Agent SIGTERM 有界退出，未完成持久化和命令结果可恢复；
- 原 `UploadClient/PremiumClient/WebullClient/RealtimeClient` 暂时作为 `LegacyProbe` 保留，仅用于对比测试，不能进入最终生产配置。

### G-02 统一 Clock、Scheduler 与交易阶段

实现可注入时间的 `ClockService` 和 `ScheduleCoordinator`：

- 使用明确时区；墙钟决定业务时点，单调钟决定 timeout/freshness；
- 支持工作日、跨日窗口、启动 catch-up、睡眠唤醒、时钟回拨和 DST；
- 每个 job 有稳定 ID、当日执行记录、幂等键、deadline、retry policy 和 missed-run policy；
- 调度只发事件，不在调度器内执行网络、磁盘或 SDK 阻塞动作；
- 首期忠实保留旧程序 weekday-only 语义，节假日日历单独升级。

**完成条件**

- 虚拟时钟覆盖 08:30、09:00、09:10、09:15:05、09:15:30、午休、14:57、15:00、15:06、16:00 及所有 Upload 夜间任务；
- 跨日常驻、周末、休眠跨过触发点和进程重启不会重复执行不可重复任务；
- UI 能显示下一触发时间、上次结果、是否补跑及判定原因。

### G-03 数据、凭据、通知和兼容服务底座

- 模块独立 SQLite/文件目录、schema migration、原子写、备份和磁盘阈值；
- Keychain/0600 secret reference，UI 不回显值；
- 统一 PushPlus/系统声音/弹窗队列，但去重、限流和过期策略由各模块提供；
- 提供可复用的有界 HTTP/WS/TCP/UDS server 组件；管理面只走 owner-only UDS；
- 保留现有 command journal、revision、幂等和审计能力。

### G-04 原生 UI 数据通道

- UI 不再经本机 8080/8421/18765/6787 读取本模块状态，而是通过 Agent UDS 接收 typed snapshot/event；
- 现有 `ModulePages.cpp` 页面和交互尽量保留，只替换数据提供者；
- 兼容端口只服务外部消费者，不成为 UI 内部依赖；
- 所有详情窗口订阅有引用计数，关闭即释放；表格 latest-only 合并且有界。

### G-05 无旧程序依赖验收

- 配置 schema 删除 `ownership=shadow|owner` 对旧程序的生产语义，改为 `engine=native|disabled`；
- 删除生产配置中的 `managed_processes`、旧 `launchd_units` 和旧路径；
- 加入 bundle 扫描、child-process 审计和旧目录不可见测试；
- 保留单独的回退 runbook，但回退脚本不得被四合一运行时自动调用。

完成 G-00 至 G-05 后，才允许开始第一个业务引擎。

## 8. 模块四：实时申购赎回原生化（最后做）

该模块涉及 Wind 私有 ABI 和 QMT 下单，风险最高，安排在前三个引擎和总体底座稳定之后。

### R-01 `RedemptionEngine` 数据状态机

- 原生实现 7 标的状态、首帧基线、变化判定、篮子换算、actionable 规则、合并通知和冷却；
- 原生实现 history、watchlist、名称、快照和 6787 兼容只读服务；
- 调度采用 G-02，保持 09:00/09:10/09:15:05/09:15:30/15:00；
- 现有 `RealtimeClient` 只用于旧结果对照，最终 UI 直接消费 engine。

### R-02 Wind Probe Helper

- 将 C probe 和必要的 ABI 描述复制到本工程，构建包内 `machome-wind-probe-helper`；
- helper 只负责进程识别、attach/capture/unsubscribe，canonical event 交给 Engine；
- timeout 后 helper 可被终止，但不 SIGKILL Wind；Wind 未确认退出时绝不清 dylib；
- ABI/offset/build 不匹配必须 fail closed。

### R-03 PCF、通知和存储

- 原生实现交易所锁、8 秒间隔、20 秒 timeout、403/429/503 cooldown、15 分钟重试和每日上限；
- old-cache/stale、方向关闭、完整篮子和 `limit=0` 语义一致；
- 历史、PCF、设置和通知状态迁移到新数据目录。

### R-04 QMT1/QMT2

- 复用当前 C++ `QmtClient`，移入 RedemptionEngine 上下文；
- 两链独立重连，必须完成 welcome + orders + positions 全同步；
- 下单只允许 UI 双击、qty=1、全局二次确认、5 秒节流；
- fixture 阶段使用 fake QMT，真实下单能力默认编译/配置双重关闭；
- 任何 unknown outcome 先强制全量对账，不自动重发。

### R-05 验收

- 13 列主表、历史、PCF 四页、QMT 两页和设置全部由四合一原生 UI 提供；
- Wind/QMT/PCF golden 和调度边界全部通过；
- 旧 `ETFMonitorHost` 和旧 Python 目录不可见时完整运行；
- 真实环境先只读，再订阅，最后才单独审批 QMT mutation；
- Wind helper 卡死/崩溃不影响另外三个模块。

## 9. 串行顺序、停线门槛和最终验收

推荐严格顺序：

```text
G 总体底座
  → P Premium A
  → U Upload
  → W Webull
  → R 实时申赎
  → I 全量集成与长稳
```

Premium 先做是因为现有核心已经是 C++，能以最低迁移风险验证 engine 接口；实时申赎最后做是因为包含 Wind 私有 ABI 和真实下单边界。每个阶段只有在以下条件全部满足后才能交给下一位 Agent：

- 该阶段代码只在本工程内修改；
- 新旧对比 fixture 全通过；
- 默认测试不访问生产端点、不发通知、不上传、不下单；
- 无旧路径、旧 label、旧二进制依赖；
- CTest 和模块专项测试通过；
- 文档更新“已完成/未完成/风险/下一任务”；
